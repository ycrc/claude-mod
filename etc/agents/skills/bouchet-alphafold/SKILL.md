# Bouchet AlphaFold workflows

## Mandatory two-stage resource workflow

AlphaFold should be run as batch jobs on Bouchet. **Do not hold a GPU while generating MSAs/data-pipeline output.**

YCRC documents AlphaFold as two resource-distinct stages:

1. **MSA/data pipeline** — CPU-only.
2. **Modeling/inference** — GPU.

Submit the CPU stage first, then run the GPU stage only after the CPU stage succeeds. This split is required to avoid idle-GPU enforcement.

A dependency is appropriate when both scripts are ready:

```bash
first_job=$(sbatch --parsable alphafold_msa.sh)
sbatch --dependency=afterok:"$first_job" alphafold_model.sh
```

Do not combine both stages into one GPU allocation merely for convenience.

## Version and module discovery

- AlphaFold 2 and AlphaFold 3 are both provided as YCRC modules and use different inputs/flags.
- Do not hard-code a remembered module version as current. Discover available versions with `module avail AlphaFold/` and choose the version appropriate to the workflow.
- Module setup and the AlphaFold command must occur in the same coding-agent shell invocation when testing interactively because agent shell calls do not preserve module state.

## AlphaFold 2

- Input is FASTA.
- The MSA stage uses CPU resources and `--msas_only`.
- The GPU modeling stage consumes the already generated MSAs with `--use_precomputed_msas`.
- `--model_preset=monomer` or `--model_preset=multimer` must match the input/workflow.
- Multiple FASTA files may be supplied as a comma-separated list.
- Runtime depends strongly on sequence length; size walltime from the workload rather than copying a template blindly.
- Treat GPU model constraints in documentation examples as examples tied to software/hardware at that time. Use `bouchet-gpu` and current module/software requirements rather than blindly copying an old constraint.

## AlphaFold 3 on Bouchet

- Before running AF3, the user must obtain their own model parameters under the AlphaFold 3 weights Terms of Use and place the parameters in a `models` directory in the working area. Do not attempt to obtain or redistribute the weights for them.
- AF3 uses JSON input rather than the AF2 FASTA-only workflow.
- The CPU MSA/data-pipeline stage uses `--norun_inference`.
- The GPU inference stage uses the data generated by the first stage and `--norun_data_pipeline`.
- YCRC configures the database location through the module/environment; do not invent a database path.
- Discover the current AF3 module with `module avail AlphaFold/` rather than assuming the version shown in an example remains current.

## Slurm and GPU policy

- CPU MSA/data-pipeline work belongs in a CPU batch partition appropriate to its runtime/resources.
- GPU inference must explicitly request a GPU.
- Do not use an interactive production GPU allocation for AlphaFold. If short interactive GPU debugging is genuinely required, follow `bouchet-gpu`; production AlphaFold should be batch-oriented.
- Do not evade YCRC GPU-utilization enforcement. If the GPU sits idle during preprocessing, the workflow is structured incorrectly; split the stages.
- Priority Tier remains paid. If the user wants an AlphaFold stage submitted or moved to `priority_*`, route through `bouchet-priority` and obtain explicit confirmation before the billable action.

For YCRC-derived detail and example flags, read `references/alphafold-ycrc.md`.
